# 歌曲预热与下载

「音源与设置 → 歌曲预热与下载」默认每个启用播放区提前准备 3 首，后台同时准备 2 首，单首最多 4 路下载。可分别设置 0–10、1–4、1–8；预热数量设 0 关闭预热。设置保存在既有 Settings JSON，旧配置自动补默认值。

预热只选择已通过审核、处于 queued 的歌曲，按实际调度的插队公平规则选取：连续两首优先歌曲后，有普通歌曲时先选普通歌曲。多个播放区轮流分配预热名额。正在播放和正在准备的任务先处理，不等待预热扫描；同一歌曲准备共享任务与缓存，轮到播放不重复下载。

预热不占用新的插队额度，不改变排队状态。完成前检查当前队列状态，取消、拒绝或已开始播放的任务不会重新写回 queued。原请求和解析后的歌曲 ID 均检查黑名单；预热缓存也必须再次通过播放前检查。失败保留原因，60 秒后允许再次预热，轮到正式播放仍会尝试。网页显示「预热中」「已预热」「预热失败」。

## 后端分段

对可并行音频地址先请求 bytes=0-0。只有返回正确 206、文件至少 2 MiB、具备强 ETag 或 Last-Modified、无内容编码时才开启分段。每段核对 Content-Range、总大小、文件版本、实际字节数，并按明确偏移写入。范围或版本异常时取消所有分段、等写入停止、清空临时文件，再用同一音源完整下载。go-music-dl 的动态流式接口始终单连接，避免多次触发上游下载。

不支持 Range 时复用首次返回的完整响应；小文件或缺少版本标记时使用单连接。单文件最多 200 MiB，并受缓存限制约束；下载整体上限 180 秒。网络地址仍通过现有域名 / 公网 IP 检查，私有地址只有明确配置的受信任音源服务可以使用。双栈连接采用地址轮换，避免先选 IPv6 不通导致长时间等待。

下载完成后计算完整 SHA-256，并检查真实音频格式、实际时长、试听片段与歌曲身份；完整音频校验失败才走下一个音源。原平台链接与 ID 的优先规则保持不变，不因预热或并行下载而改为搜索同名歌曲。缓存保护待播、准备、播放及正在写入的任务，未引用的历史缓存按访问时间清理。

## Agent 下载

预热发生在后端。后端通知播放时，Agent 将缓存音频下载到本机，2 MiB 以上最多四路，旧后端不支持正确 Range 时回退单连接。每次请求带设备凭证和媒体票据，不跟随重定向；所有分段取消后才回退写入。合并文件大小与 SHA-256 均正确后交给 mpv，不重新编码。制动、租约到期、连接断开或新播放任务取消当前下载，取消不触发回退。

## 排查慢在哪里

| 日志 / 显示 | 含义 |
| --- | --- |
| 音源取源日志 | 平台解析与备用源等待；增加下载连接数无法缩短这部分 |
| media.download.parallel | 是否实际开启分段、连接数、文件总大小 |
| media.download.progress / complete | 字节数、速度、连接等待及传输时间 |
| media.validation.metadata / ok | 文件真实码率、采样率、时长及验证耗时 |
| media.preload.start / ready / failed | 预热范围与准备结果 |
| Agent「开始下载 / 下载完成」与控制台速度 | Linux 后端到 Windows 电脑的传输 |

无损音源体积通常更大，预热只能提前后端下载，无法保证公网链路带宽。优先按日志区别音源解析、上游传输、校验和 Agent 下载，再调整预热和连接数。上游只支持单连接、限制速度或无稳定版本标记时，不会强行多路。
